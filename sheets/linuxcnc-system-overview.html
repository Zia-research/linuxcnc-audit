LinuxCNC — the whole system on one page

From the operator's screen down to the machine. Domains are marked by lines, never by frames — a frame asserts membership and can be contradicted by its own geometry, while a line cannot. Two dotted grey lines bracket what is inside the computer; between them, two dashed red ones bracket the scheduling boundary, and what lies in that band is the two shared-memory segments, which is what shared memory is. The frames that do exist assert process and thread membership — a fact about the running system, not a domain — and each lies wholly on one side of every line. It began as a merge of two earlier sheets — Sheet B of the errata sheet for component detail, the context sheet's rebuilt view for the seams — and has been corrected twelve times since, each correction and its evidence recorded at the foot of the page.

Sources: sheets/linuxcnc-code-notes-errata.html (Sheet B, the corrected block diagram — milltask internals, the emcmot segment's three structures, TC_QUEUE, the joint pipeline, component and driver inventories, the boundary wording) and sheets/linuxcnc-context-diagram.html ("Rebuilt from the code" — the linuxcncsvr / milltask process split, the three UI-side clients separated by what they touch, motion as functs inside the servo thread, the base-thread condition, the config column). Both verified against the pinned clone caa13ca6ae. Assembled 2026-08-06.

Restructured 2026-08-07, after three defects found by reading the geometry rather than looking at the figure. (1) The two domain containers claimed a membership their geometry did not hold: the frame labelled "ordinary Linux processes" ended at y=240, while linuxcncsvr (246) and milltask (300) sat below it — the same defect a reader had already caught in the sibling colour figure, fixed there and never here. (2) The emcmot segment was drawn wholly above the boundary, saying it belongs to ordinary scheduling. (3) HAL shared memory was not drawn at all, only captioned inside the realtime frame, which asserted it belongs to the realtime domain. Both segment claims are false: each is created on one side and attached from the other — motion.c:827 → usrmotintf.cc:578, and hal_lib.c:285 → halcmd.c:107, an ordinary process. The fix removes both domain frames. A dashed line marks the boundary and nothing else, the two shared segments are drawn across it, and the two connectors that used to land on a frame edge — from halcmd and from the .hal files — now land on HAL shared memory, which was always their real target. A line cannot make defect (1): there is no container left to contradict. (4) A fourth defect, found by a reader questioning the layout rather than the drawing: linuxcncsvr sat in a vertical chain between the NML triplet and milltask, which asserts that commands transit through it. They do not. In configs/common/linuxcnc.nml every process is LOCAL — emc, emcsvr and xemc alike — and only emcsvr carries server?=1 master?=1; task attaches the SHMEM segments directly, read-write. linuxcncrsh has no entry at all and opens its own channels. linuxcncsvr's two real jobs are creating the segments and starting first (scripts/linuxcnc.in:795) and serving them over TCP 5005 (emcsvr.cc:185 calls run_nml_servers(); its man page: "Allows network access to LinuxCNC internals via NML") — and its clients are remote, so none of them appears on this figure. The figure also contradicted itself: it already ran the GUI and linuxcncrsh straight to the triplet while routing task around. It is now drawn beside the triplet, and the triplet connects directly to milltask. (5) The same question asked once more exposed a label that was wrong twice: linuxcncrsh was captioned “NML over the network”. It is neither. On the network side it speaks a plain-text telnet protocol on its own port — emcrsh.cc:187 sets port = 5007, and :373-390 call socket(), bind() and listen(): it is itself the server, not a client of one. Its own header calls it an “Extended telnet based LinuxCNC interface”, and its man page “a text-mode interface for commanding LinuxCNC over the network… using telnet(1), nc(1) or similar”. On the LinuxCNC side it is an ordinary local NML client: emcrsh.cc:41 includes shcom.hh, which opens the channels as "xemc" — LOCAL in the default config — so it does write the triplet directly. It has no relationship with linuxcncsvr whatever: two independent servers, TCP 5007 text and TCP 5005 NML. The box is relabelled and both network doors are now drawn, because a door to the network that is not shown is a door nobody thinks about. Both now sit on the top edge, so that where the network touches this machine is visible at a glance; the canvas was widened and halcmd / halshow moved right to free the lane its own descent needs. Which door a client uses decides what it must be, and the difference is larger than it looks. The NML door is the narrow one. It carries no port of libnml — src/libnml/ has no Windows or Apple build — and no NML library is packaged apart from LinuxCNC, so “a remote NML client” means in practice another Linux running LinuxCNC as a GUI-only control PC. Even then it is not free: axis.py:75-78 gates AXIS's HAL component on the AXIS_NO_HAL environment variable, and HAL is local shared memory, so a remote AXIS must set it and give up its jog pins, pyvcp panels and classicladder detection. The shipped instructions have also rotted: client.nml still says to run tcl/tkemc.tcl, a GUI no longer present in the tree — only its screenshots survive in the documentation. The telnet door is the wide one: a socket and some text, so Windows, macOS, a tablet or a three-line script all qualify. Anything resembling MES, SCADA or a phone app belongs there, not on the NML side. A vocabulary warning, because it inverts easily: NML calls the machine the master — emcsvr carries master?=1 in server.nml — so describing the remote GUI as the “master PC” contradicts the very file you would then open. The two doors also differ in posture: linuxcncsvr authenticates nothing at all, while linuxcncrsh has a connection and an enable password (emcrsh.cc:189, default "EMCTOO") that its man page warns twice are “sent in the clear”. Red marks what is wrong rather than what is. Two problems on the NML door — it authenticates nothing, and its two config files look unmaintained — and one under the triplet, where the number itself lives: client.nml and server.nml declare emcStatus at 10240 B against the default's 20480, while NML gives a message only half the declared buffer (cms.cc:729-731). That last one is printed unverified on the figure itself, because sizeof(EMC_STAT) was never measured — a diagram that hides its own uncertainty is worse than one that admits it. The first words of the note scope it to the networked configs, so no reader concludes the default is affected. Also moved: “not NML on the network side” left the linuxcncrsh box for the grey peer above it. The phrase never described the box — it described the wire, and the grey box is what sits at the other end of it. (6) The GUI's link to HAL was drawn one-way. Reader's catch, and the source is blunt: halui.cc creates 47 HAL_IN pins against 42 HAL_OUT (:494, :531), and even axisui has inputs — axis.py:3961-3964 exports notifications-clear and resume-inhibit as HAL_IN alongside its twelve HAL_OUT jog pins. A GUI panel with a button writes a pin; the same panel's lamp reads one. Now double-headed. The remaining six one-way arrows were audited rather than left alone, and all six survive: the wizards generate the INI and HAL files, task reads the INI without writing it, a .hal file is loaded into HAL memory, and the two short arrows into tpmod / homemod / *kins are calls — the box says “called from motmod's functs”, which is one-way by construction. (7) The networked configs are not merely stale — they are not installed. src/Makefile:745-746 copies only linuxcnc.nml and linuxcnc_big.nml into $(prefix)/share/linuxcnc. A user installing from a package never receives client.nml or server.nml; they exist for whoever reads the source tree, which is why nothing exercised them and nothing caught the drift. The red note on the NML door says so, because “unmaintained” understates it. And the telnet door now carries its own red line: it does have two passwords, but its man page warns twice that they are sent in the clear, so marking only 5005 as unauthenticated would have let 5007 read as safe. (8) The chain stopped at the servo thread. Every connector endpoint was resolved by computation to the box that contains it, and the result was blunt: hardware drivers had exactly one connector and it pointed down, to the machine; base-thread, stepgen.make-pulses and the whole “HAL components in the same thread” row had none at all. Following the arrows, a reader could descend from the operator as far as motion and then stop — the drivers and the machine were an island nothing reached. Worse: HAL shared memory carried four connectors and all four arrived from the non-realtime side — GUI, halui, halcmd and the .hal files — so the box straddled the boundary to claim a reach from both domains while the graph showed it used from one. Two links now close it, the servo thread to HAL memory and HAL memory to the drivers, both double-headed and both at the weight of the emcmot link because they are the same kind of path. The loop really does close there: motion.c:753 exports joint.N.motor-pos-cmd as HAL_OUT and :754 joint.N.motor-pos-fb as HAL_IN, while a driver is itself a HAL component — hal_parport.c:542 and hostmot2.c:1807 both call hal_init(), and hostmot2 exports .read (:1710) and .write (:1717), the two ends of the bracket the shipped configurations write by hand. The link goes to HAL memory and not from motion to the drivers, which would assert a transit that does not happen — defect (4) again, in a new place. The lesson refines the one below, and does not repeat it: this was neither geometry nor a misread label but topology, and a script could have caught it years earlier had anyone written it. diagramCheck asks whether every arrow lands on a named box; it never asks whether every box is reached by an arrow. The first question finds dangling arrows, the second finds dangling boxes — and only the second could have found this one. Still open from the same pass: milltask exports fourteen HAL pins (taskclass.cc:43-56, three IN and eleven OUT) and still has no line to HAL memory, and the base thread still has none to anything. (9) Every arrow into the NML triplet was double-headed, and not one of the pairs they touched is two-way. The strip is drawn as three named cells, which invites a per-channel reading, while each connector landed on whichever cell its box happened to sit above. configs/common/linuxcnc.nml:16-28 settles it without a line of C++: it declares an access mode for every process/channel pair. The GUI was drawn reading emcCommand, declared W. milltask was drawn reading emcStatus, declared W. And linuxcncrsh — a program whose whole purpose is commanding the machine over a socket — was drawn writing emcError, declared R, with no command arrow anywhere on the figure. The one pair genuinely declared RW, task on emcCommand, was the only one no arrow touched. The three client boxes turn out to be the same client: AXIS opens its channels as "xemc" (emcmodule.cc:973, :1642), halui likewise (halui.cc:292, :303), and linuxcncrsh inherits it through shcom.hh (emcrsh.cc:41) — so one declaration line covers all three: W command, R status, R error. And linuxcncsvr holds the same hand — W, R, R. It is not a fourth kind of participant but a proxy carrying a client's permissions for whoever connects on TCP 5005, which is why its command-write had to be drawn: without it the remote NML client reaches linuxcncsvr and the path stops, defect (8) in another place. The first fix was twelve one-way arrows, one per declared pair. It was correct and it was unreadable — halui sits left of the strip and linuxcncsvr right of it, so four of the twelve needed doglegs, and three of those crossed the milltask lanes. A figure that states the truth and cannot be read has traded one defect for another. So the cells went instead, and the double heads came back. The two dividers are deleted; the triplet is one box. Against an undivided triplet a double head is simply true — every client writes commands and reads status and errors, task does the exact mirror — and with no named compartment for an arrow to point at, the per-channel claim can no longer be made, rightly or wrongly. The channel names, their sizes and their directions all survive as text inside the box, which is where a claim this fine-grained belongs. That is the same move as removing the two domain frames, for the same reason, and it is the principle stated at the head of this page applied a second time: a subdivision asserts something its own geometry can contradict. Delete the subdivision and the contradiction becomes unrepresentable — it is not repaired, it is made impossible to state. One nuance kept off the figure for width: the config grants task RW on emcCommand, but emcCommandBuffer->read() at emctaskmain.cc:3303 is its only application use; that W belongs to the transport (queue confirm_write serial), not to the program. The method note outlasts the fix: diagramCheck cannot see this class of error at all. The strip is one rect and its cells are two lines, so the checker's model of the figure is coarser than the claims the figure makes — it can only ever confirm that an arrow reached the strip. The per-channel audit was therefore computed apart from the drawing, against the config table. (10) “Except under RTAI” was published, and it was wrong. The caption on the scheduling boundary named the whole of RTAI as the exception that turns the line into a kernel boundary. RTAI has two backends and only one of them does: LINUXCNC-FINDINGS.md §2.8 lists five RTAPI flavours, and uspace/RTAI (uspace_rtai.cc) runs realtime as user-space threads — where the sentence's own claim still holds. Only RTAI kernel (rtai_rtapi.c + rtai_ulapi.c) loads kernel modules. The exception was overstated by four flavours out of five. It surfaced while asking whether the sentence was worth keeping at all: the question was about economy, the answer turned out to be about accuracy. This repository has already been corrected in public once over an RTAI framing (issue #1, and the reporter was right); a second one was sitting on the figure, unremarked, in the published copy. Defects (4) and (5) share a lesson worth more than either: both were found by a reader questioning what the drawing asserted, and neither was reachable by any checker here — diagramCheck measures boxes, it does not read labels. (11) The figure moved into a drawing editor, and this page is now generated from that file. Ten passes of correction had all been made by editing SVG by hand, which meant the one person who could move a box was the one who could not see the result. The drawing is now a .drawio file, and a converter regenerates only the <svg> block — this footer and its evidence make no round trip and so cannot be damaged by one. The code citations left the drawing. Line numbers on arrows are proof, and proof belongs in LINUXCNC-FINDINGS.md; a figure is for understanding. Each citation was therefore checked into the findings file first and deleted from the figure after, replaced where it carried meaning by a short phrase. Colour became a rule rather than a habit — a small number of families, each with a stated meaning — and the rules are drawn on the sheet as a legend, so a reader can test them against the boxes instead of taking them on trust. Part of (9) is hereby reversed, and the guarantee it rested on is replaced by a better one. The NML triplet is again drawn as three named compartments, because a reader asked to see the three channels, their sizes and their access modes where they belong. The old argument — “with no named compartment for an arrow to point at, the per-channel claim can no longer be made” — no longer holds, since the compartments are back. What replaces it is checkable rather than structural: no connector lands on a compartment. All five NML edges target the parent box in the model, which a script can re-test on every save, where the old guarantee could only be asserted once and then trusted. Also this pass: the scheduling boundary became a band — two red lines with the shared memory lying between them, which states more exactly what the single line stated before; rtapi_app is drawn as a frame containing the threads that run inside it, the first frame on this sheet since (1) removed the domain frames, and it asserts process membership rather than a domain, wholly on one side of every line; and both items left open by (8) are closed — milltask has its line to HAL memory, and the base thread is no longer joined to nothing. (12) Four layout defects fixed — including one the note above had argued was not there — and the repair of another broke something the checker then caught. (11) shipped with three faults recorded rather than hidden, and they are now fixed. What they were: the drivers-to-machine link descended through both lines of the addf-order note; halcmd's descent to HAL memory passed through the halrmt box, which on a figure that means something by adjacency is the worse of the two, since a line through a box reads as a line to it; and the two red boundary lines spanned the whole canvas, so the scheduling band ran behind the legend panel and appeared to cut through the key that explains it. The first now leaves its box on the left and descends outside the rtapi_app frame, the second drops straight down a lane of its own, and the boundary lines stop short of the legend. The third was invisible to every check here, and that is a consequence of a deliberate choice: boundaries are drawn as <line> rather than <path> so the connector check does not report the intended crossings as collisions — a checker that cries wolf on every run stops being read — and the price of the exemption is that this one had to be seen. It was, in a rendering. Then the repair introduced a new defect, and this time the checker found it. Rerouting the first link left its arrow seven units short of the box it starts from: draw.io shortens a line to make room for its own arrowhead, and the converter pulls the endpoint back onto the border afterwards — except that the export rounds coordinates to the unit, the first segment came out one unit off true, and the code decided whether a segment was horizontal or vertical by exact equality. Neither branch matched, nothing was reported, and the result was a connector starting in open space and a Machine hardware box that no path reached. The test is a tolerance now. The verdict went FAIL → clean on the same file inside one pass, and that is the only evidence worth much: a check that has just failed and then passes says more than one that has only ever passed. diagramCheck() now reports clean on three consecutive runs — 32 boxes, 182 texts, 24 connectors. A fourth defect was argued away instead of fixed, and the argument was wrong. An earlier pass reported the HAL-to-servo link crossing the RTAI-flavours caption. Measuring in the browser put the caption's left edge at x=825.5 against the connector's x=815, and the report was written off as an artefact of whichever font had loaded. Measured again, on the same two files, the caption runs from x=781.3 to 1218.7: the connector was inside it, and it was the first measurement that had resolved a narrower fallback face — 349 units of text against 437. The crossing was real all along. A second oracle that shares the first one's environment is not a second oracle: getBBox and the checker disagreed about the verdict while agreeing about the font, so measuring more carefully in the same browser could only ever reproduce the same accident more precisely. The link now runs through the corridor between base-thread and the frame's own caption — 31 units clear against the widest rendering observed and more against the narrow one. The repair is geometry that survives either font, not an argument about which font is right, and the general form of that is worth more than this instance: when a check's verdict depends on the environment, make the drawing robust to the range, rather than picking the reading that lets you leave it alone.
